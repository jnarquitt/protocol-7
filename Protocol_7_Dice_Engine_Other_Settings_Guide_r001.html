Protocol Dice Engine

HOW TO RUN IT IN OTHER SETTINGS

The resolution mechanic under Protocol 7 — named dice, no flat modifiers, every die explainable — was built as a general-purpose engine, and The Continuance Files is one skin on top of it. This is the toolkit for building another. Reference baseline: v0.188 core dice math.

The Engine, and the Skin On Top of It

Everything a GM needs to reskin lives in one distinction. Keep it in mind through the rest of this guide:

Protocol 7's own setting content — Vectors, Aletheia, the six Abilities named STR/DEX/CON/INT/WIS/CHA, the 40-Skill registry, VAMs — is all skin. None of it is required for the engine to work. That's what makes reskinning possible without touching a single formula.

Build a New Skin — Step by Step

  1. Pick your Attribute set. Protocol 7 uses six (STR/DEX/CON/INT/WIS/CHA). Five or six both work cleanly against a 3-Attribute-per-roll pattern; below four gets thin, above seven starts diluting what each roll says about the character.
  2. Build the trained-thing list (Protocol 7 calls these Skills) and link each one to 1–3 Attributes. Repeating an Attribute across two links on the same roll is intentional, not a bug — it's how the engine says "this Attribute matters a lot here."
  3. Name your special-resource layer (Protocol 7's VAM). Decide what it represents in-fiction, and give it a capacity budget with its own name (Protocol 7's BAR). Keep the rule that it only ever adds a die when a specific entry explicitly says so — never an implied bonus.
  4. Set your Gear rule. Default is one primary-relevant Gear die per roll. Raise the limit only for a gadget-forward genre (see Chrome Static below), and say so explicitly — don't let it drift upward table by table.
  5. Decide your Mastery fiction. A trained-thing hitting the die ceiling doesn't get a bigger die (there isn't one past the ceiling) — it unlocks a second, identical die, gated behind something explicit in your setting (a rite, a root-access boot sequence, a clearance level). "Mastered but dormant" — trained past the ceiling with no active access — should be a real, nameable state in your skin, the same way Protocol 7 flags it rather than silently ignoring it.
  6. Decide what earns Advantage/Disadvantage in your genre's tone. Keep the mechanic identical (add/remove one die, cancel 1-for-1); only the trigger list changes.
  7. Reskin the blank-face flavor. One sentence is enough — see the worked skins below for the pattern.
  8. Leave the math alone unless you have a reason and can simulate it. Reskin fiction, not formulas — this is the single most important rule in this whole guide.

Guardrails

Never add a generic bonus-die slot or a flat numeric modifier. Protocol 7's core data explicitly locks this off (generic_bonus_die_slot: false, routine_flat_numeric_modifiers: false, all_pool_changes_require_named_source: true). Every die in a pool must be traceable to a specific, nameable reason. The moment a skin allows "+2 because reasons," it has stopped being this engine and become a different game wearing its die ladder.
Safe to retune per skin: the die ladder's ceiling, the Attribute count, the trained-thing list's size, the special-resource budget formula, the Gear limit (with a stated reason), and how many trained-thing Ranks a level grants. None of these touch the blank-face rule or the no-modifiers rule, so none of them require new simulation to stay balanced — they change scope, not shape.

Status

This toolkit follows Protocol 7 v0.188's core dice math as its reference baseline. If that baseline's blank-face rule, die ladder, or Advantage/Disadvantage handling changes in a later playtest revision, this guide's Core Math section needs a matching update — the worked skins and the step-by-step build process don't reference any version-specific numbers beyond that section, so they carry forward unchanged.
