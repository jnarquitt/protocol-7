# Protocol 7 v0.188 — Playtest Governance & Guardrails

**Status:** ACTIVE PROCESS AUTHORITY
**Purpose:** This file is the first process document to read before any substantial Protocol 7 rules, app, rulebook, database, audit, or release work.

## GitHub-first operating law

Protocol 7 project continuity lives in the repository, not in conversational memory.

Before substantial work, the working assistant must read the current repository authorities relevant to the task. Conversation memory may help locate material, but it is not authoritative evidence for a rule or process when a repository authority exists.

When a new process decision, guardrail, mechanical lock, or superseding rule is established, record it in the repository during the same work cycle whenever practical. Do not rely on remembering it in a later chat.

## v0.188 playtest philosophy

v0.188 is a PLAYTEST release, not a final standards specification.

The purpose of governance is to prevent accidental regression and internal contradiction while allowing deliberate experimentation.

### Hard guardrail: no resurrection

A mechanic that has been deliberately superseded must not return merely because it appears in an older rulebook, app, document, database, summary, or memory.

Older material is useful as a feature/reference baseline only when it has not been superseded.

### User decisions

Explicit user decisions and locks are authoritative until the user reopens them or playtest evidence gives a compelling reason to propose reopening them.

### Assistant design authority for playtest gaps

The assistant is authorized to fill unresolved gaps with thoughtful v0.188 playtest rules without stopping for approval on every decision.

Such decisions must:
- fit the established Protocol 7 design language;
- avoid resurrecting superseded mechanics;
- remain internally consistent with current rules;
- be clearly treated as v0.188 playtest decisions rather than falsely described as ancient canon;
- be easy to revise after reading/playtest feedback.

### Dice-math requirement

Any new or materially changed mechanic involving dice probabilities, pool size, success distribution, Advantage/Disadvantage, Mastery, critical-style outcomes, matched results, or other probability-sensitive behavior must receive mathematical analysis or simulation before being promoted as a playtest rule.

The design text should not make probability claims that have not been checked.

### Non-dice design requirement

BAR costs, VAM organization, advancement pacing, Edges, conditions, gear, and other non-probability systems require deliberate design review and consistency checking, but not historical proof for every choice.

## Authority model for v0.188

The target publication authority is the v0.188 playtest rulebook plus its synchronized canonical rules source.

Supporting databases, the application, interactive guide, QA tests, and reference documents derive from that authority. They do not independently redefine the rules.

During the rebuild, candidate databases may contain experiments. Presence in JSON alone does not make a mechanic canon.

## Auditor role

The Auditor is a hard-ass continuity reviewer, but its job is practical rather than bureaucratic.

At major milestones it must ask:
1. Did an obsolete/superseded mechanic return?
2. Do the rulebook, canonical rules source, app, guide, databases, and QA disagree?
3. Does any probability-sensitive rule make claims unsupported by math/simulation?
4. Did implementation invent a mechanic that the rules do not contain?
5. Did a current playtest decision fail to propagate to dependent products?
6. Are there contradictions that would confuse a player or GM at the table?
7. Are unresolved experiments clearly identified rather than silently treated as settled rules?

Agreement among several downstream files is not sufficient if they all copied the same stale or invented rule. The audit must compare against current locks and supersession records.

## Current v0.188 hard locks established in conversation

These must be reflected in the current rules authority before publication:

- Ordinary Skill die progression caps at d12.
- Progression beyond the ordinary d12 Skill die is replaced by Skill Mastery rather than larger ordinary Skill dice.
- Mastery is a separate dice source and requires a Mastered Skill plus legal explicit access; it is intended to make six-die capability an expensive/high-level character option.
- There is no generic bonus-die slot.
- Gear may add dice when specifically relevant under its rules.
- VAMs may add dice only when their rules explicitly say so; a VAM die is not automatically Advantage.
- Advantage and Disadvantage are separate pool-adjustment mechanisms. The GM may award them from circumstances and specific rules may trigger them. Players are encouraged to use tactics, preparation, teamwork, resources, and knowledge to create Advantage.
- Flat numeric bonuses such as +2 are not the normal design language; dice-facing effects should be used where an additive benefit is needed.
- Movement is 30 feet per AP spent: 1 AP = 30 ft, 2 AP = 60 ft, 3 AP = 90 ft. There is no universal Run action that costs 3 AP and doubles movement.
- Vitality Ritual: roll each of the six Ability dice once. If any die shows 4+, starting HP = 18 + highest face. With the Level 1 starting array ordinary starting HP is 22–26. If all six dice show blanks (1–3), starting HP = 28. If multiple Abilities tie for the highest qualifying result, the player chooses the tied Ability representing Vitality Origin.
- Matched Blanks / broader Dice Tricks concepts are not required for v0.188 publication unless explicitly reactivated; unresolved experimental effects must not silently enter core resolution.
- v0.188 application is phone-first. Except for the Vector name, ordinary character creation and play should not require keyboard typing. Mechanical purchases and counters use touch controls such as +/- buttons, steppers, cards, toggles, and selectors.
- The successful functionality and automation of the prior app are a product reference and should be preserved or improved where compatible with v0.188; a clean rebuild is not permission to replace useful game controls with generic forms.

## Publication workflow

For a substantial v0.188 publication pass:
1. Read this governance file first.
2. Read current explicit locks/supersession authorities.
3. Read the current canonical rules source and target rulebook source.
4. Reconcile obvious contradictions without reopening settled decisions.
5. Fill genuine playtest gaps thoughtfully under the authority above.
6. Run math/simulation for probability-sensitive additions or changes.
7. Synchronize canonical rules source and player-facing rules.
8. Run an Auditor pass focused on regression, contradictions, math, and propagation.
9. Regenerate/update app and guide from the resulting rules authority.
10. Publish as a playtest build and expect iteration.

## Check-in policy

Work in large, efficient passes. Do not interrupt the user for routine implementation decisions that can safely be made under this authority. Check in when a substantial reviewable milestone is ready or when a genuinely consequential decision cannot be made without changing the game's intended identity.

### Continuation shorthand

When the user sends only **`kk`**, interpret it as: **approved; recommendations accepted; continue on the current path; make reasonable decisions; do not stop for commentary unless genuinely necessary.** The shorthand is authorization to continue the current approved workstream, not permission to ignore the repository authorities or supersession guardrails above.
