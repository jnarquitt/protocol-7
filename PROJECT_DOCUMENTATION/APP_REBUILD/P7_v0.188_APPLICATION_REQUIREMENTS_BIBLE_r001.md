# Protocol 7 v0.188 — Application Requirements Bible r001

**Status:** PRE-IMPLEMENTATION DESIGN AUTHORITY — requires Auditor review before coding
**Date:** 2026-08-23

## 1. Mission

Build the Protocol 7 v0.188 Interactive Character & Play App as a clean implementation using one authoritative character-state model and one authoritative roll builder.

The application is rebuilt **from scratch at the implementation level**, but it is **not redesigned from scratch as a product**. The current v0.187 application is the known-good visual, interaction, and feature reference. Preserve successful behavior and familiar organization unless this specification explicitly changes it.

No v0.187 mechanical code is authoritative merely because it exists. v0.188 rules come from the current candidate authority map and synchronized rule documents.

## 2. Product goals

The app must:
- make Protocol 7 playable at the table without requiring constant rulebook consultation;
- make character creation fast for a new player;
- make a preconfigured Vector even faster;
- make the dice pool visually understandable before the roll;
- enforce BAR, authorization, Mastery, advancement, and dice-source rules rather than merely displaying them;
- remain usable on a phone in portrait orientation by an adult with imperfect eyesight or limited hand dexterity;
- preserve character data reliably;
- expose no contradictory duplicate mechanical state;
- provide clear routes to the Protocol 7 project home and Jade Lion Studios hub.

## 3. Architectural law

### P7-APP-ARCH-001 — One character state
There shall be exactly one authoritative persisted character object for current character mechanics.

### P7-APP-ARCH-002 — One roll builder
All player-facing rolls shall be constructed through one canonical roll-builder service/function. No screen may independently recreate dice-pool logic.

### P7-APP-ARCH-003 — Derived values are derived
Maximum HP, BAR ceiling, authorization, current Ability dice after advancement, available Mastery slots, and similar values shall be calculated from canonical inputs. They shall not be maintained as competing manual values.

### P7-APP-ARCH-004 — Rules data separated from UI
VAM definitions, presets, Level progression, die ladder, Skills, gear rules, and other catalog data shall be data structures consumed by the interface rather than repeated prose constants across screens.

### P7-APP-ARCH-005 — Versioned persistence
Saved data shall include schema version and rules version. Migration behavior must be explicit. v0.187 saves must never be silently interpreted as fully valid v0.188 characters.

### P7-APP-ARCH-006 — No hidden numeric modifiers
Roll construction shall not introduce flat +1/+2/etc. bonuses where the rules require dice-facing effects.

## 4. Canonical character-state requirements

The persisted model must support at minimum:

### Identity
- character name;
- player name;
- pronouns/identity notes if used;
- concept/background;
- optional portrait reference if later supported;
- notes.

### Progression
- Level 1–6;
- advancement history sufficient to audit Level choices;
- Level 2 Edge;
- Ability increases at Levels 3 and 5;
- Mastered Skills at Levels 4 and 6.

### Abilities
- STR, DEX, CON, INT, WIS, CHA;
- base assigned die;
- advancement steps;
- current derived die;
- d12 ceiling.

### Vitality / HP
- six individual Vitality Ritual faces;
- recorded Vitality Origin;
- exceptional all-blanks state;
- derived starting HP;
- derived current maximum HP;
- current HP;
- Durable Edge contribution where applicable.

### Skills
- Skill name/category;
- rank/current Skill die as required by Engine rules;
- current three associated Ability dice or canonical Ability relationship;
- Mastered status;
- notes/permissions where required.

### VAM / BAR
- current BAR ceiling by Level: 16 / 18 / 21 / 24 / 27 / 30;
- current authorization band;
- loaded VAM IDs;
- total loaded BAR;
- preset/loadout definitions;
- field-swap state/cost where play tracking requires it.

### Play resources
- AP current/max;
- Reaction availability;
- current HP;
- Exposure/mission state if retained by current rules;
- temporary conditions;
- ordinary bonus-die source state where needed;
- once-per-session Edge usage;
- other per-session resources required by synchronized rules.

### Gear
- equipped/available gear;
- weapon/effect dice data;
- tags/permissions;
- notes.

## 5. Character creation workflow

### P7-APP-CHAR-001
Character creation shall offer **Preconfigured Vector** and **Custom Vector** as equally legitimate starting paths.

### P7-APP-CHAR-002
Preconfigured characters shall immediately populate legal Abilities, Skills, VAMs, gear, and other required starting data, while remaining editable where the rules permit.

### P7-APP-CHAR-003
Custom creation shall enforce the starting Ability multiset: d8, d8, d6, d6, d4, d4.

### P7-APP-CHAR-004
Custom creation shall track the 20 starting Skill Ranks and prevent accidental overspend.

### P7-APP-CHAR-005
Level 1 VAM loading shall enforce 16 BAR and Standard authorization.

### P7-APP-CHAR-006
Unused BAR is legal. The app shall not invent filler VAMs or require the player to reach exactly 16 BAR.

## 6. Vitality Ritual

### P7-APP-VIT-001
The app shall present the Vitality Ritual as a deliberate character-creation ritual, not as a hidden calculation.

### P7-APP-VIT-002
The player rolls each assigned Ability die individually in order: STR, DEX, CON, INT, WIS, CHA.

### P7-APP-VIT-003
The app shall allow entry of the six individual faces and validate each face against the die assigned to that Ability. A d4 cannot record 7, for example.

### P7-APP-VIT-004
If at least one face is 4+, starting HP = 18 + highest face.

### P7-APP-VIT-005
Ordinary starting HP therefore ranges from 22–26 under the starting array.

### P7-APP-VIT-006
If all six faces are blanks (1–3), starting HP = 28 and the exceptional result is visibly identified.

### P7-APP-VIT-007
If multiple Abilities tie for highest, the player may choose which tied Ability is recorded as Vitality Origin.

### P7-APP-VIT-008
The interface shall briefly explain that Vitality Origin is interpretive and does not claim that the winning Ability literally equals physical toughness.

### P7-APP-VIT-009
Maximum HP at later Levels is derived as starting HP + 4 per Level after Level 1 + 5 if Durable has been selected.

## 7. Advancement

### P7-APP-ADV-001
Level may range only from 1 through 6.

### P7-APP-ADV-002
Every Level after 1 grants +4 maximum HP and +4 Skill Ranks.

### P7-APP-ADV-003
Level 2 unlocks one Edge.

### P7-APP-ADV-004
Level 3 grants one Ability die increase by one step.

### P7-APP-ADV-005
Level 4 grants the first Mastered Skill.

### P7-APP-ADV-006
Level 5 grants the second Ability die increase by one step.

### P7-APP-ADV-007
Level 6 grants the second Mastered Skill.

### P7-APP-ADV-008
Ability step ladder is d4→d6→d8→d10→d12. d12 is the ceiling.

### P7-APP-ADV-009
Advancement must be reversible/editable for playtest correction without leaving impossible derived state.

### P7-APP-ADV-010
The app shall warn before a Level reduction that invalidates VAM authorization, BAR load, Ability growth, Mastery, or an Edge. It shall not silently destroy choices.

## 8. Edge requirements

### P7-APP-EDGE-001
The Level 2 Edge list shall be driven from canonical rules data.

### P7-APP-EDGE-002
Driven shall track once-per-session use if the app supports session resource tracking.

### P7-APP-EDGE-003
Inspired shall enter the roll builder as the ordinary bonus-die source and must obey the one-ordinary-bonus-die slot.

### P7-APP-EDGE-004
Prepared and Connected shall provide a usage control and concise reminder rather than pretend their fictional permission is an automatic roll success.

### P7-APP-EDGE-005
Durable permanently adds 5 maximum HP and has no renewable session-use control.

## 9. BAR and VAM requirements

### P7-APP-VAM-001
BAR ceiling by Level is 16, 18, 21, 24, 27, 30.

### P7-APP-VAM-002
The VAM catalog shall use the final rebuilt v0.188 catalog as data authority.

### P7-APP-VAM-003
Each VAM shall have stable ID, name, family, BAR cost, authorization requirement, rules text, and machine-readable mechanical tags sufficient for the app behavior it creates.

### P7-APP-VAM-004
The selector shall hide or clearly lock VAMs above current authorization. It shall explain why they are unavailable.

### P7-APP-VAM-005
The app shall prevent loading VAMs above current BAR capacity.

### P7-APP-VAM-006
Loading a VAM into unused BAR capacity is free.

### P7-APP-VAM-007
Replacing already-loaded VAMs during play costs 1 AP for the entire field swap, not 1 AP per VAM.

### P7-APP-VAM-008
Character-building/reconfiguration outside active play shall not accidentally charge AP unless the rules explicitly require it.

### P7-APP-VAM-009
The BAR meter shall update immediately when VAMs are loaded/unloaded.

### P7-APP-VAM-010
Presets shall immediately load their VAMs and update the live BAR meter.

### P7-APP-VAM-011
All 14 Level 1 final-candidate presets shall be available and legal at Level 1.

### P7-APP-VAM-012
A preset is a convenience, not a class. The player may legally alter the resulting loadout.

## 10. Skill Mastery

### P7-APP-MAST-001
Mastery begins at Level 4 with one Mastered Skill and expands to two Mastered Skills at Level 6.

### P7-APP-MAST-002
A Mastered Skill possesses a Mastery Die equal to its current Skill die.

### P7-APP-MAST-003
The Mastery Die is dormant unless a legal Mastery-access mechanism, such as an appropriate VAM, permits access.

### P7-APP-MAST-004
Only the Mastery Die belonging to the Skill currently being rolled may enter the pool.

### P7-APP-MAST-005
Two Mastered Skills never contribute two Mastery dice to one roll.

### P7-APP-MAST-006
The roll builder shall visibly label a Mastery Die when present so the player understands why the pool contains it.

## 11. Canonical roll-builder requirements

### P7-APP-ROLL-001
Before rolling, the app shall display the components of the pool, not merely the final number of dice.

### P7-APP-ROLL-002
The pool shall distinguish:
- Skill die;
- Ability dice;
- ordinary Bonus Die, if any;
- Mastery Die, if any;
- explicit exceptional sources, if a future rule permits them.

### P7-APP-ROLL-003
At most one ordinary Bonus Die may enter a routine roll. Multiple ordinary sources do not stack into extra routine dice.

### P7-APP-ROLL-004
A legal Mastery Die occupies its own source category and does not consume the ordinary Bonus Die slot.

### P7-APP-ROLL-005
The app shall explain rejected/competing bonus sources rather than silently dropping them.

### P7-APP-ROLL-006
The dice shown before the roll shall be the dice actually rolled.

### P7-APP-ROLL-007
Changing an Ability, Skill, VAM, Edge, gear item, condition, or Mastery permission must immediately change every dependent roll where applicable.

### P7-APP-ROLL-008
No screen may manually add a sixth/seventh die outside the roll-builder rules.

### P7-APP-ROLL-009
Protocol Dice scoring and any Matched Blanks behavior shall be implemented only after the release authority explicitly states whether Matched Blanks is included in v0.188.

## 12. Play screen

### P7-APP-PLAY-001
The Play screen is optimized for repeated table use, not character editing.

### P7-APP-PLAY-002
It shall keep current HP, max HP, AP, Reaction, BAR, key conditions, and commonly used rolls/actions visible with minimal navigation.

### P7-APP-PLAY-003
Running costs all 3 AP and permits up to double normal movement under the current locked rule.

### P7-APP-PLAY-004
VAM field swap shall expose the 1-AP whole-swap cost clearly during active play.

### P7-APP-PLAY-005
The app shall not force the player to visit a Rules tab for ordinary action resolution.

## 13. Navigation and information architecture

Target primary navigation:
- Character
- Skills
- VAMs
- Gear
- Play
- Advancement

Rules are not a primary app tab. Provide a clear link to the Interactive Rules Guide.

### P7-APP-NAV-001
Primary navigation shall remain reachable without returning to the top of a long page.

### P7-APP-NAV-002
On phone layouts, bottom navigation or an equivalently persistent control shall be available.

### P7-APP-NAV-003
The current tab/screen shall be visually obvious.

### P7-APP-NAV-004
The app shall include a persistent or easily accessible **Protocol 7 Home** control.

### P7-APP-NAV-005
Protocol 7 Home shall provide a route onward to **Jade Lion Studios**.

### P7-APP-NAV-006
No major product screen may become a navigation dead end.

## 14. Mobile, accessibility, and usability requirements

### P7-APP-UX-001
Design phone portrait first, desktop second.

### P7-APP-UX-002
No required gameplay interaction may depend on hover.

### P7-APP-UX-003
No horizontal page scrolling at supported phone widths.

### P7-APP-UX-004
Interactive targets should be approximately 44 CSS px minimum in their primary touch dimension where practical.

### P7-APP-UX-005
Body text shall remain comfortably readable for older players; do not use thin/light fonts for important headings or controls.

### P7-APP-UX-006
Critical information may not rely on color alone.

### P7-APP-UX-007
Dice labels shall include textual identity/value information sufficient to distinguish them without color.

### P7-APP-UX-008
Common Play interactions should generally require no more than two deliberate taps from the Play screen.

### P7-APP-UX-009
Long catalogs such as VAMs require search/filter/family grouping or similarly fast navigation.

### P7-APP-UX-010
Destructive reset/delete operations require confirmation and must say exactly what will be lost.

### P7-APP-UX-011
Form validation shall appear near the problem and explain the fix in ordinary language.

### P7-APP-UX-012
The app shall remain useful with limited fine-motor precision: avoid tiny icons as the sole control, tightly packed selectors, or gesture-only functions.

## 15. Visual canon

Use v0.187 as the visual reference, formalized as follows:

- dark Protocol 7 presentation;
- red/black foundation with restrained dark-gold/yellow emphasis;
- high-contrast readable body copy;
- heavier headers;
- card-based grouping for major functional areas;
- clear live meters for HP/BAR/AP where appropriate;
- dice displayed as prominent physical/game objects, not tiny metadata;
- visual density suitable for phones without becoming a sparse modern banking app;
- avoid excessive decorative background art behind functional controls;
- state changes should be obvious but not animated excessively.

### P7-APP-VIS-001
Visual polish may not obscure rules state.

### P7-APP-VIS-002
The UI shall prioritize the physicality/readability of dice pools.

### P7-APP-VIS-003
The generic Protocol Dice Engine may later reuse the shell, but Protocol 7 branding and BAR/VAM terminology must remain implementation-specific data/content rather than hardwired ecosystem assumptions.

## 16. Save, export, and recovery

### P7-APP-DATA-001
Changes shall save locally without requiring an account.

### P7-APP-DATA-002
The user shall have a clear way to export/backup character data in a portable representation before public promotion.

### P7-APP-DATA-003
Import shall validate schema/rules version and reject or explicitly migrate incompatible data.

### P7-APP-DATA-004
A reset shall distinguish character reset from application/settings reset if both exist.

### P7-APP-DATA-005
No application update may intentionally destroy an existing saved character without an explicit migration or export warning.

## 17. Rules explanation inside the app

The app is a play tool, not a second full rulebook. Use concise explanations at decision points.

Required contextual teaching includes:
- what the Vitality Ritual is doing;
- why HP is not merely Constitution;
- what the dice in a pool physically represent;
- why a bonus source is or is not entering a roll;
- why a VAM is locked;
- why a Mastery Die is dormant or active;
- what an advancement choice changes.

Deep explanations link to the Interactive Rules Guide.

## 18. QA gates

Implementation proceeds through mandatory gates.

### Gate A — Requirements audit
The Auditor reviews this Bible for contradictions, missing rules, ambiguous requirements, and impossible acceptance criteria. No production implementation before disposition of BLOCKER findings.

### Gate B — Data model
Build and test canonical state, derived selectors, catalog data, save/load, and migration behavior without visual polish.

### Gate C — Functional skeleton
Character creation → Vitality → Skills → VAM loadout → Play roll → advancement → Mastery must work end-to-end.

### Gate D — Mechanical QA
Run automated/manual scenario tests at Levels 1, 2, 3, 4, 5, and 6, including illegal-state attempts and adversarial optimization cases.

### Gate E — Mobile/usability QA
Test representative narrow phone, larger phone, tablet, and desktop layouts. Verify touch targets, scrolling, persistent navigation, readability, and common-action tap counts.

### Gate F — Visual implementation
Apply final visual canon only after mechanics and information architecture are stable.

### Gate G — Auditor release review
Fresh evidence pass against every applicable requirement ID. Any BLOCKER prevents promotion.

## 19. Minimum acceptance scenarios

The final QA matrix must include at least:

- Create a legal custom Level 1 Vector with exactly the starting Ability multiset and 20 Skill Ranks.
- Load a 15-BAR Medic preset and confirm unused BAR remains legal.
- Attempt to exceed 16 BAR at Level 1 and receive a clear rejection.
- Complete a Vitality Ritual whose highest face is INT 7 and receive 25 starting HP with INT available as Vitality Origin.
- Complete all six blanks and receive exactly 28 starting HP.
- Advance a 25-HP character to Level 6 and receive 45 maximum HP before Durable.
- Select Durable and receive 50 maximum HP in that case, with no session-use control.
- Increase an Ability at Levels 3 and 5 and verify every dependent roll uses the current die.
- Attempt to increase d12 and receive a legal-choice requirement rather than d14 or silent failure.
- At Level 4, Master one Skill but confirm no Mastery Die enters a roll without legal access.
- Add legal Mastery access and confirm exactly one labeled Mastery Die enters that Skill's roll.
- At Level 6, master two Skills and confirm a roll never receives both Mastery dice.
- Present two ordinary bonus sources and confirm only one enters the pool.
- Load VAMs into unused BAR without AP cost outside active field swapping.
- During active play, replace loaded VAMs and charge exactly 1 AP for the whole field swap.
- Use Running and charge all 3 AP.
- Navigate from every primary screen to Protocol 7 Home and from there to Jade Lion Studios.
- Reload the browser and recover the same character state.
- Export, reset, import, and recover an equivalent character.

## 20. Non-goals for first rebuild

Unless separately authorized, the first clean v0.188 rebuild does not require:
- cloud accounts;
- multiplayer synchronization;
- GM campaign management;
- server database;
- native mobile packaging;
- animated 3D dice;
- speculative AI features;
- unrelated redesign of Protocol 7 branding.

The goal is a dependable, comprehensible, portable web application that accurately implements the game.

## 21. Definition of success

The rebuild succeeds when a player can create or load a Vector, understand the character by looking at the dice and resources on screen, play a session without fighting the interface, advance from Level 1 through Level 6 without creating illegal state, and have every displayed mechanical result trace back to one canonical rules/data path.

The application should feel like **Protocol 7 made tangible**, not a digital character sheet with Protocol 7 labels pasted onto it.
