## Findings register

### APPREQ-001 — MAJOR — Skill advancement representation remains underspecified
The requirements state +4 Skill Ranks each later Level but do not yet fully define how rank accumulation maps to Skill die changes inside the app's canonical data model.

**Consequence:** A developer could store only a displayed die and lose auditable rank progression, or store ranks without a canonical derived die rule.

**Disposition:** Data-model phase must import the authoritative Engine Skill-rank→die relationship before implementing Skill advancement. Mark UNVERIFIED until sourced from Engine authority.

### APPREQ-002 — MAJOR — VAM machine behavior must not be inferred from prose names
The rebuilt 84-VAM catalog is mechanically rich. Requirement VAM-003 correctly demands machine-readable tags, but those tags do not yet exist as a canonical data artifact.

**Consequence:** Hand-coded `if(vam.name===...)` logic would recreate the duplication problem the rebuild is meant to solve.

**Disposition:** Before functional VAM UI, create a canonical v0.188 VAM data file with stable IDs and explicit effect metadata. Human-readable catalog remains rules authority; data file must be audited against it.

### APPREQ-003 — MAJOR — Matched Blanks release state is deliberately unresolved
ROLL-009 correctly refuses to assume Matched Blanks belongs in v0.188.

**Consequence:** The roll-result component needs an extension point but must not implement provisional effects as canon.

**Disposition:** Build result parsing so blank-pattern handling is modular/off by default until release authority resolves inclusion.

### APPREQ-004 — MINOR — `Vitality Origin` terminology is still development-facing
The HP brief says Vitality Origin may be called that during development and final setting-neutral/player-facing terminology may change.

**Disposition:** Treat label as configurable content, not schema identity. Persist the selected Ability, not the phrase `Vitality Origin` as a hard semantic key.

### APPREQ-005 — MAJOR — migration cannot be designed from wishful compatibility
The new app must not silently import v0.187 saves. The exact v0.187 persisted schema must be inspected before a migration converter is promised.

**Disposition:** First clean build may support native v0.188 export/import while marking v0.187 migration as unsupported until a separate schema audit is complete. This does not block the functional skeleton.

### APPREQ-006 — MINOR — home/studio URLs must remain configurable
Do not scatter absolute navigation URLs through components. Define navigation destinations once in app configuration so repository/Pages moves do not create dead links.

### APPREQ-007 — NOTE — accessibility requirements are appropriately stronger than the old app
The phone-first, no-hover, large-touch-target, no-color-only-state, and persistent-navigation requirements are consistent with the project's known usability goals and should not be weakened during visual polish.

## Three most embarrassing contradictions if ignored

1. A player gains +4 Skill Ranks but the app changes a Skill die using an invented conversion rule.
2. A VAM's prose says one thing while a hand-coded name check makes it do another.
3. The rebuilt app proudly claims clean architecture while silently importing an incompatible v0.187 save into the wrong fields.

## Promotion recommendation

Proceed to **Gate B — Data Model**, not visual implementation.

Gate B must specifically resolve APPREQ-001 and establish the data architecture required by APPREQ-002. APPREQ-003 remains an intentional release decision. APPREQ-005 may remain deferred if the app clearly labels v0.187 migration unsupported rather than pretending compatibility.

**Do not begin full visual polish yet.**
