## Findings

### GATEB-001 — FIXED — Skill progression ambiguity
The canonical v0.187 structured source explicitly supplies the rank breakpoints. The app model now persists ranks and derives Skill dice centrally.

**Status:** FIXED.

### GATEB-002 — GREEN — one-state architecture
The proposed character schema persists base Ability assignments, advancement choices, Vitality faces, Skill ranks, loaded VAM IDs, gear, and mutable play state. Derived values are explicitly prohibited from becoming competing editable state.

**Status:** GREEN.

### GATEB-003 — GREEN — Vitality preserves starting Ability context
The derived-state contract correctly requires Vitality face validation against the starting assigned Ability die, not a later advanced Ability die. This prevents retroactive invalidation/benefit when Core Growth changes an Ability.

**Status:** GREEN.

### GATEB-004 — MAJOR — machine-readable VAM catalog not yet instantiated
The VAM data contract is sound, but the actual 84 VAM entries have not yet been transcribed into a machine-readable catalog and audited against the human-readable final candidate.

**Risk:** Functional VAM behavior cannot be trusted until IDs/effects/prerequisites are concrete data rather than prose interpretation.

**Required action:** Build `P7_v0.188_VAM_CATALOG_DATA_r001.json` containing all 84 entries and perform one-to-one catalog audit.

### GATEB-005 — MAJOR — Mastery with multi-die Skill expressions remains unresolved
At 15+ ranks, Skills become multi-die expressions (`d12+d4` etc.). The current Mastery concept says the Mastery Die equals the current Skill die, but “die” becomes ambiguous when the Skill itself is two dice.

**Risk:** A Level 4–6 character with a highly advanced Skill could receive an invented or inconsistent Mastery implementation.

**Required action:** Resolve in Protocol Dice Engine authority before implementing Mastery for multi-die Skill expressions. Until resolved, the app must fail closed with an explanatory warning rather than invent behavior.

### GATEB-006 — MINOR — gear classification must be synchronized before roll-builder completion
The v0.187 pool order includes a primary gear die, while the v0.188 bonus-source taxonomy discusses ordinary Bonus Die competition. The final clean implementation needs an explicit classification matrix distinguishing the core primary gear contribution from Feature/Assist/situational bonus sources.

**Required action:** Create a short dice-source classification authority before Gate C mechanical completion.

### GATEB-007 — NOTE — Matched Blanks modularization is correct
Matched Blanks remains disabled in central rules data and the result pipeline provides an extension point without treating provisional effects as canon.

## Three most embarrassing contradictions if ignored

1. A rank-15 Mastered Skill receives a made-up Mastery die because nobody defined what “equal to the Skill die” means once the Skill is `d12+d4`.
2. The VAM screen looks complete but actual behavior is driven by improvised name checks rather than the audited 84-entry catalog.
3. Gear is simultaneously treated as the normal primary gear contribution and as a competing ordinary Bonus Die, causing pools to lose or gain a die depending on which screen launches them.

## Gate disposition

Proceed with **Gate C preparation only**:

- instantiate and audit the 84-VAM machine catalog;
- resolve multi-die Skill Mastery at the Engine level;
- resolve the primary-gear versus ordinary-bonus source classification;
- then construct the functional skeleton around the already-approved canonical state/derived-state contracts.

No visual implementation blocker was evaluated because visual work remains intentionally deferred.
