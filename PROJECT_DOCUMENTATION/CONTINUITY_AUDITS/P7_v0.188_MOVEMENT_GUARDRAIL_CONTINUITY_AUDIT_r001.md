## Executive verdict

**RED — FAIL**

The guardrail chain failed. A stale movement rule was inserted into candidate canonical data, repeated into the Application Requirements Bible, converted into an acceptance test, and then implemented in the mobile app. Multiple layers agreed with one another while being wrong relative to the preserved canonical predecessor and current designer authority.

## Findings register

### MOV-001 — BLOCKER — stale Run rule promoted into candidate canonical data

- Affected: `P7_v0.188_RULES_DATA_CORE_r001.json` pre-fix.
- Conflict: contained `run_ap_cost:3` and `run_move_multiplier:2`.
- Evidence: v0.187 snapshot explicitly identifies `30-foot repeatable Moves with no universal Run`.
- Consequence: downstream code can be internally consistent while mechanically wrong.
- Disposition: replace Run fields with explicit 30-feet-per-AP repeatable movement and prohibit universal Run.
- Status: **FIXED in rules-data core r002 content**.

### MOV-002 — BLOCKER — requirements document repeated stale rule

- Affected: `P7_v0.188_APPLICATION_REQUIREMENTS_BIBLE_r001.md`, PLAY-003.
- Conflict: states that Running costs all 3 AP and permits double normal movement.
- Consequence: implementation teams following requirements are instructed to build the wrong mechanic.
- Disposition: supersede PLAY-003 with Movement Authority r001; revise Requirements Bible in its next clean revision.
- Status: **OPEN / SUPERSEDED BY EXPLICIT MOVEMENT AUTHORITY**.

### MOV-003 — BLOCKER — QA matrix tested the wrong behavior

- Affected: Acceptance Matrix r001 A26.
- Conflict: passing test required the obsolete 3-AP/double-movement Run rule.
- Consequence: QA would certify the defect rather than catch it.
- Disposition: replace A26 with 30/60/90-foot movement tests and explicit no-Run regression test.
- Status: **FIXED in Acceptance Matrix r002 content**.

### MOV-004 — BLOCKER — mobile r003 implements stale Run control

- Affected: `v0188-mobile-r003.html`.
- Conflict: exposes `RUN · SPEND 3 AP · ×2 MOVE` and sets AP to zero.
- Consequence: player-facing development behavior is mechanically false.
- Disposition: r003 is regression evidence only and must not be promoted. Next mobile build must replace Run with AP-priced 30/60/90-foot movement controls.
- Status: **OPEN**.

### MOV-005 — MAJOR — audit process validated agreement instead of provenance

- Affected: milestone audit practice.
- Conflict: earlier review treated agreement among newly created v0.188 artifacts as evidence of correctness without tracing the rule to the preserved predecessor/lock.
- Consequence: a copied error became self-reinforcing across data, requirements, tests, and code.
- Disposition: add provenance regression checks: every changed hard mechanical constant must be compared against predecessor authority and must identify an explicit authorized change when different.
- Status: **OPEN; new A42 regression test added as first guardrail**.

## Continuity stress questions

**Was the stale Run rule canonical merely because several v0.188 files contained it?** No. Those files shared a common unverified source and therefore reproduced one defect.

**Did a newer authorized decision create Run?** No evidence was found. The preserved v0.187 snapshot says the opposite, and the designer explicitly reaffirmed 30 feet per AP.

**What are the three most embarrassing contradictions if r003 shipped?** (1) the app says Run while predecessor canon says no universal Run; (2) QA explicitly passes the wrong Run behavior; (3) the requirements document itself instructs implementation of the defect.
