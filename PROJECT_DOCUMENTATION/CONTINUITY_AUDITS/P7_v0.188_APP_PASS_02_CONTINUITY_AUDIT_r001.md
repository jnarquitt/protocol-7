## Executive verdict

**RED — FAIL for promotion. AMBER — acceptable as an internal prototype.**

The runtime-overlay strategy successfully demonstrates the desired advancement UI and protects the live v0.187 app, but it is no longer an acceptable foundation for the final v0.188 player-facing application. The inherited source contains too many mechanically authoritative v0.187 assumptions for a patch layer to guarantee continuity.

The candidate may continue to exist as a prototype/reference. Do not promote it and do not deepen the overlay architecture.

## Findings register

### APP-001 — BLOCKER — two competing mechanical data models
**Affected:** candidate loader, inherited v0.187 app, Pass 02 patch.

The inherited app still owns character state under v0.187 assumptions while the patch owns advancement state under v0.188 assumptions. Max HP, BAR, Ability growth, VAM legality, and Mastery are therefore not represented by one authoritative data model.

**Consequence:** the UI can display a correct v0.188 value while underlying calculations, saves, or other tabs still operate on v0.187 data.

**Required disposition:** build a full v0.188 source fork with one state model. Do not attempt to solve this through more DOM overrides.

**Status:** OPEN.

### APP-002 — BLOCKER — VAM legality is not enforceable in current overlay
**Affected:** VAM tab, rebuilt 84-VAM candidate catalog, Level-based authorization.

Pass 02 changes the displayed BAR ceiling but leaves the old VAM catalog and selection logic in place. It cannot reliably enforce Standard/Advanced I/High Integration/Advanced II/Elite/Continuance authorization or guarantee that every loaded VAM belongs to the current candidate catalog.

**Consequence:** an apparently legal v0.188 sheet can contain illegal or obsolete VAMs.

**Required disposition:** integrate the rebuilt catalog as structured application data in the full fork and validate every loadout against both authorization and BAR.

**Status:** OPEN.

### APP-003 — BLOCKER — Core Growth does not change authoritative Ability state
**Affected:** Advancement tab, Vector/Ability picker, all Skill pools using Ability dice.

The patch records a manual `from` die rather than deriving and updating the actual Ability die. This permits contradictory states, such as recording DEX d8→d10 while the actual sheet remains d6 or d10.

**Consequence:** displayed advancement and actual roll pools can disagree.

**Required disposition:** Core Growth must mutate the same Ability object used by every pool calculation, with a recorded advancement history and d12 ceiling.

**Status:** OPEN.

### APP-004 — BLOCKER — Skill Mastery is visual only
**Affected:** Mastered Skill state, Mastery-capable VAMs, Roller.

The patch can label a Skill Mastered but cannot determine whether the relevant Mastery VAM is loaded and cannot inject the correct Skill Mastery Die into the actual roll.

**Consequence:** the signature Level-4/6 progression mechanic is not playable from the candidate app.

**Required disposition:** integrate Mastered Skill state, VAM prerequisites, and roll construction inside one roll builder.

**Status:** OPEN.

### APP-005 — MAJOR — stale player-facing rules remain visible
**Affected:** inherited Rules, Vector, VAM, and other explanatory surfaces.

Pass 02 adds override notices but leaves obsolete v0.187 text visible, including CON×3 HP and fixed 16-BAR explanations.

**Consequence:** a player must know which rule text to ignore. That is unacceptable in a commercial-facing rules app.

**Required disposition:** full fork must remove or rewrite stale text rather than annotate around it.

**Status:** OPEN.

### APP-006 — MAJOR — Edge state is only partially implemented
**Affected:** Driven, Inspired, Prepared, Connected, Durable.

The patch tracks used/ready status for renewable Edges and calculates Durable HP, but it does not integrate Driven/Inspired into the actual roll flow or give bounded table workflow for Prepared/Connected.

**Required disposition:** integrate Edge actions into Play/Roller with explicit consumption/reset behavior.

**Status:** OPEN.

### APP-007 — MAJOR — candidate localStorage migration is not a final migration plan
**Affected:** browser persistence.

Separate storage is correct for prototype safety, but the final fork needs a deliberate migration/export/import strategy for existing v0.187 players. Silently mixing schemas is prohibited.

**Status:** OPEN.

### APP-008 — NOTE — runtime loader is useful as a regression reference
The loader has value as a visual/prototyping harness because it proves the advancement surface can coexist with the v0.187 layout. Preserve it as development material even after the full fork is created.

## Three most embarrassing contradictions if shipped today

1. The app can simultaneously tell a player their maximum HP comes from the Vitality Ritual and still contain inherited mechanics/text deriving HP from Constitution.
2. A Level 1 or Level 2 character can appear to have a larger/smaller legal BAR ceiling while the inherited VAM selector remains unaware of v0.188 authorization bands and catalog membership.
3. The app can display a Mastered Skill and an Ability increase that do not actually alter the dice rolled for that character.

Any one of these would be sufficient to reject public promotion.

## Promotion recommendation

**Do not continue deepening the runtime overlay.**

Proceed instead with a **full v0.188 source fork** using the v0.187 app as the known-good UI/feature baseline, but replace the mechanical data model deliberately:

1. create a single v0.188 character-state schema;
2. implement Ability, Skill, Vitality/HP, Level, Edge, BAR, VAM authorization/catalog, Mastery, gear, AP, Reaction, Exposure, and mission state in that schema;
3. rebuild roll construction around Core Pool + one ordinary Bonus Die + optional legal Mastery Die;
4. port existing v0.187 UI/features onto that state model;
5. provide explicit migration/import rather than shared storage assumptions;
6. run functional QA and a second Auditor review before changing public redirects.

**Audit disposition: RED for promotion; GREEN to begin full-source rebuild.**
